  - `DcbCriteria` reads (`DcbCriteria.all()`, type-only criteria) exclude stream-only events (#280/ADR 49): a `dcbTags`-exists guard, backed by a sparse index on the Mongo array field.
  - `StreamCatchupSubscriptionModel`/`ReactorStreamCatchupSubscriptionModel` (`@StreamSubscription`) exclude DCB events (#282/ADR 50): a `Filter.capability(EventStoreCapability.STREAM)` guard ANDed into both the replay read and the live handover filter, via a new `Filter.CapabilityFilter` case.
  - `@Subscription`/`Subscriptions` were revived (previously deprecated stream-only aliases) as the capability-neutral default (#283/ADR 51): the same position-based catch-up as stream, minus the capability guard, routed through a new `AgnosticSubscriptionFilter` marker. Delivers both stream and DCB events, filtered only by type, catching up over the unified global position (ADR 45) and resuming via `GlobalCheckpoint`.
  - The write-time invariant that makes the Mongo capability filter sound: `write(...)` (the stream API) now rejects any event carrying the `dcbtags` CloudEvent extension, in all four stores. This closes a real gap Copilot's review caught: the Mongo `Filter.capability(DCB)` check keys off the *derived* `dcbTags` array field (Mongo-only, written only by DCB `append(...)`, sparse-indexed per ADR 49), not the `dcbtags` CloudEvent extension (present on any tagged event regardless of write path, which is what the in-memory matcher and `DcbCloudEvents.isDcbEvent` check). Without the write-time guard those two could diverge; with it they are provably equivalent, so the Mongo filter can use the indexed field without missing a stream-written-but-tagged event.
  - `@DcbSubscription`/`DcbSubscriptions` were untouched throughout; they already excluded stream events correctly (`isDcbEvent` + `DcbCriteria` post-filter).
- **DcbDecider couples a Decider with its DCB boundary and tags (merged to main as #289, ADR 0052).** `DcbDecider<C,S,E>` (Java record in `dsl/dcb-dsl/common`) wraps a `Decider` plus a `Function<C, DcbCriteria>` (read boundary derived from the command, returns null when the decider does not apply, used by composition) plus a `TagGenerator<E>` (tags for the events it emits). The DSL exposes `execute(command, dcbDecider)` on both stacks, replacing the old `execute(criteria, command, decider)` extensions (the low-level `execute(criteria, function)` on the service stays). `DcbDecider` composes like `Decider` (`adapt`/`compose`): composed criteria is `DcbCriteria.anyOf` over the children that recognize the command, composed tags are their set union. Tagging is now two complementary models: a `DcbDecider` carries its own tags (per-execute, routed via a new optional `TagGenerator` on `DcbExecuteOptions`), while decider-less DCB (raw `execute`, or `@DcbTag`) uses the optional global `TagGenerator`. Precedence in `GenericDcbApplicationService.addTags` is per-execute first, then global, else it throws (never appends untagged). The global tagger is now optional at the constructor (new no-tagger constructor overloads) AND in the Spring autoconfig, which now creates the `DcbApplicationService` even with no global `TagGenerator` bean (`DcbApplicationServiceDiagnostics` removed). Course-enrollment and hotel-booking now own per-decider inline tags and have no global tagger bean; word-guessing-game's plain `dcb` module stays decider-less with a global tagger as the counter-example.

## Architecture Summary

Occurrent is a Maven multi-module JVM event-sourcing library centered on CloudEvents, designed as small composable libraries rather than a framework: domain models stay independent of Occurrent. Occurrent stores CloudEvents and provides application-service, event-store, subscription, DSL, deadline, and Spring Boot wiring helpers.

Root modules (`pom.xml`): `test-support`, `eventstore`, `subscription`, `cloudevents-extension`, `common`, `application`, `dsl`, `framework`, `deadline`, `library` (currently `hederlig`), `bom`, `example` (active-by-default `examples-module` profile).

Layering:
1. `common` + `cloudevents-extension`: reusable primitives (`Condition`, `Filter`, retry/time utilities, Mongo filter/sort conversion, stream metadata `streamid`/`streamversion`). `common/eventstore-capability` is a new, deliberately tiny, dependency-free module holding just the `EventStoreCapability` enum and the DCB tag extension name constant (`EventStoreCloudEventExtensions`); it exists because `common/filter` needs `EventStoreCapability` for `Filter.capability(...)` (added in #282) but `eventstore-api-common` (the enum's original home) already depends on `common/filter`, so the enum had to move somewhere both can reach without a cycle.
2. `eventstore`: persistence contracts and implementations. Blocking `EventStore` composes read/conditional-write/existence; wider capabilities are optional interfaces (`EventStoreQueries`, `EventStoreOperations`, `ReadEventStreamWithFilter`).
3. `application`: adapts domain events to CloudEvents via `CloudEventConverter`/`CloudEventTypeMapper`, orchestrates commands via `ApplicationService`/`GenericApplicationService`.
4. `subscription`: reacts to event streams. Blocking + reactor APIs, Mongo/native/Spring/Redis/in-memory adapters, and durable/catchup/competing-consumer wrappers.
5. `dsl`: convenience layers over the core APIs for Kotlin/Java.
6. `framework/spring-boot-starter-mongodb`(`-reactive`): auto-configures the Mongo stack.

ADRs live in `doc/architecture/decisions`, NOT `doc/adr`.

## Module Boundaries

`eventstore`: `api/common` (shared model: `WriteCondition`, `WriteResult`, `StreamReadFilter`, `SortBy`), `api/blocking`, `api/reactor`, `api/dcb`, `inmemory`, `mongodb/common`, `mongodb/dcb-common`, `mongodb/native`, `mongodb/spring/blocking`, `mongodb/spring/reactor`.

`application`: `service/blocking` (+ `dcb`), `command-composition`, `cloudevent-converter` (Jackson 2/3, XStream), `cloudevent-type-mapper`.

`subscription`: `api` (blocking/reactor contracts), `core` (shared checkpoints, filters, start positions), `inmemory`, `mongodb` (common + native/Spring + checkpoint storage), `redis` (Spring checkpoint storage), `util` (durable, stream-catchup, dcb-catchup, competing-consumer, reactor wrappers).

`framework/spring-boot-starter-mongodb`: wires `MongoTransactionManager`, `SpringMongoEventStore`, checkpoint storage, lease competing-consumer, `SpringMongoSubscriptionModel -> Durable -> Catchup -> CompetingConsumer`, DSLs, `GenericApplicationService`, Jackson 3 converter config.

## Primary Execution Flows

Application command flow: `ApplicationService.execute(streamId, ExecuteOptions, domainFunction)` -> `GenericApplicationService` resolves optional `ExecuteFilter` via the converter (filtered reads require `ReadEventStreamWithFilter`, else fail fast) -> read stream, convert to domain events, run pure domain function, convert back, write at expected version, run optional post-write side effects.

Mongo blocking write/read: `write` validates `WriteCondition` (for `anyStreamVersion`, materializes the stream so retries reuse events); inside a transaction, reads current version, validates, maps to documents with stream metadata, inserts, translates duplicate/write exceptions, returns old/new versions. Reads pin to current version to avoid skew.

Subscription flow: `Subscribable.subscribe(subscriptionId, filter, startAt, action)` -> Mongo implementations use change streams + lifecycle-managed listener containers -> `DurableSubscriptionModel` persists the checkpoint after successful action -> `CatchupSubscriptionModel` replays history for a time/position start before handing over to the live model -> Spring Boot wraps in durable/catchup/competing-consumer layers.

## Conventions And Patterns

- Java 21 baseline; Kotlin JVM target follows Java 21. Java and Kotlin coexist in most modules (root build-helper adds `src/main/kotlin` + `src/test/kotlin`).
- Public APIs are small capability interfaces, not monoliths; validate nulls/invalid args eagerly (`Objects.requireNonNull` / `IllegalArgumentException`); prefer static factories/builders for fluent APIs; Apache 2 headers on source.
- Nullness uses JSpecify (`@NullMarked`, `@Nullable`) in newer APIs, not uniformly across old code.
- Changelog (`changelog.md`): unreleased changes go under `### Changelog next version`, NOT a versioned `### X.Y.Z (date)` section. The maintainer assigns a version/date only at release. Never invent one. Update the changelog after any change affecting behavior, public API, build/runtime, or user-facing capability; skip it for doc-only edits.
- **Changelog convention for unreleased capabilities (PR #300):** a capability that is unreleased gets NO "change" entries (users never had the old behavior to change from). DCB is unreleased, so DCB dev-churn (fixes, tuning, API polish of the still-unreleased DCB) stays OUT of the `#### Changes` and `#### Details` subsections and lives only in `#### Highlights`. DCB feature-announcement bullets and non-DCB shipped changes still go in `#### Changes`/`#### Details` as normal.
- Kotlin: avoid extension names colliding with Java members (ADR 0012 uses `executeSequence`/`executeList`); typed execute filters namespaced under `ExecuteFilters` (ADR 0013); keep Java contracts honest (`? extends E`) with localized Kotlin bridge casts only where needed. Run at least `test-compile` on affected modules after Kotlin-around-Java-generics changes (`.context/lessons.md`: Kotlin inference can fail even when Java compiles).

Testing: JUnit 5 + AssertJ dominant, jqwik for a few property tests, Awaitility for async/subscription/deadline. Unit and integration tests both run under Surefire (no Failsafe split). Docker/Testcontainers (MongoDB, Redis) is common; some integration tests bind Mongo to host port `27017`.

### Restart-test pattern (reusable)

Annotation attributes (`startAt`, `resumeBehavior`, `startupMode`) are compile-time constants, and the dynamic `StartAt`/`DcbStartAt` supplier that encodes `resumeBehavior` is evaluated ONCE, inside `subscribe(...)` at bean post-processing. Pausing/resuming a running model (`stop()`/`start()`) never re-invokes it, so it cannot demonstrate replay-vs-resume. To test `resumeBehavior`, close the Spring context and boot a fresh one (`SpringApplication.run(...)`) against the same durable MongoDB backing data (same `spring.data.mongodb.uri`, same database), so the annotation is reprocessed like a real restart. See `DcbSubscriptionResumeBehaviorAnnotationMongoTest` and siblings: a `FirstBootApplication` and `SecondBootApplication` register the same subscriber classes so the second context's subscriber is a fresh instance.

### Testcontainers gotchas

- `MongoDBContainer.getReplicaSetUrl()` (no-arg) always targets the `"test"` database. Use `getReplicaSetUrl(String databaseName)` for isolation; do NOT string-concat a suffix (Mongo forbids dots in DB names and it silently stays `"test"`, causing cross-test collisions).
- Booting via `SpringApplication.run(...)` (not `@SpringBootTest`) gets no `@ServiceConnection`; pass `--spring.data.mongodb.uri=...` in the `args`.
- This repo pins the host port `27017:27017` with `.withReuse(true)` in the restart-pattern tests (see `OccurrentReactiveMongoAutoConfigurationWiringTest`). Root cause not fully isolated (likely Colima/Testcontainers flakiness), but the fixed-port+reuse pattern is reliable here.
- Mongo Testcontainers on this machine intermittently fail with `MongoSocketOpenException`/`Prematurely reached end of stream` right after container start, a known Colima networking flake (`colima.md`). Retry once before concluding a test is broken.

## Known Fragile Areas And Risks

- **Likely regression: `Decider<C, S extends @Nullable Object, E>` breaks the common Kotlin "feed the returned state into the next decide call" pattern.** Found 2026-07-10 running the rewrite recipe against `scheduling-service` (a real Parkster Kotlin consumer) as a live upgrade trial. PR #287 ("Add JSpecify nullness defaults across Java packages") added `extends @Nullable Object` to `Decider`'s `S` type parameter and kept `decideOnStateAndReturnState(S state, ...)` returning `@Nullable S`. For a concrete non-null `S` (e.g. a sealed Kotlin state interface, never conceptually nullable), Kotlin now types the return as `S?` while the same method's `state` parameter still demands non-null `S`, so `val s2 = decider.decideOnStateAndReturnState(decider.decideOnStateAndReturnState(initial, cmd), cmd)`-style chaining fails to compile. Notably, an earlier commit (`6ed6aed31`, "Removed nullable from Decider since it doesn't work all that well with Kotlin") deliberately fixed this exact problem once before, so #287 appears to have reintroduced it. Not a rewrite-recipe issue (nothing in the recipe touches `Decider.java` or nullness), so this was reported to the user rather than papered over in the recipe or in the trial project. Needs its own investigation/fix in `dsl/decider/src/main/java/org/occurrent/dsl/decider/Decider.java` before release if Kotlin ergonomics matter for 0.30.0.
- **Real-upgrade-trial method validated: install the reactor as `-Drevision=0.30.0-SNAPSHOT`, then run the recipe against a real downstream consumer via `mvn org.openrewrite.maven:rewrite-maven-plugin:RELEASE:run -Drewrite.activeRecipes=org.occurrent.UpgradeToOccurrent_0_30 -Drewrite.recipeArtifactCoordinates=org.occurrent:occurrent-rewrite:0.30.0-SNAPSHOT`.** No pom edits needed to run the recipe itself (ad-hoc invocation). Confirmed correct behavior on `scheduling-service` (100% Kotlin, uses `decider`/`view-dsl`/`occurrent-support`): the recipe was a clean no-op since that project never referenced any renamed 0.20.5 symbol directly, and the View DSL's `evolveAll(events: Sequence<E>)` overload removal (part of #314) was the one real Stream/Sequence-to-List break found, fixed trivially by swapping `queryForSequence` to `queryForList` at the one call site feeding `evolveAll` (documented Kotlin-manual bucket, not a recipe gap). When trialing against a real repo with pre-existing uncommitted work, stash it first (`git stash push -u`), revert only your own trial changes with `git checkout --`, then `git stash pop` to restore the original state exactly.

- **DCB partition stream-version collision retryability is MongoDB-version-sensitive (#297).** On a DCB+STREAM store, two concurrent DCB appends to disjoint boundaries can collide on the same stream version when they hash to the same partition. On MongoDB 4.2.8 (the pinned integration-test version) this collision surfaces as a transient `WriteConflict`, auto-retried. On newer server versions it can instead be a non-transient `E11000` duplicate-key error, which the #297 fix now detects (via the `streamid_1_streamversion_1` index name on the error) and rethrows as retryable rather than letting it fail as a misleading `DuplicateCloudEventException`. The pending Mongo test-version bump (see Release Readiness) validates this against realistic (non-4.2.8) behavior.
- **The DCB API surface was frozen for release per ADR 0053.** Do not casually change DCB public types/signatures without checking that ADR first.

- **Docker/Testcontainers is the biggest verification risk.** `colima.md` and `nordvpn.md` document Ryuk/Mongo timeout/network issues. Fixed `27017:27017` bindings can clash with local Mongo or concurrent runs. Async subscription tests are timing-sensitive (Awaitility).
- **Catch-up to live handover invariant (ADR 0014/0008).** `CatchupSubscriptionModel` reconciles events written during the bulk replay via a delta query using `SortBy.natural(DESCENDING)` + `limit` (insertion order), NOT the time-based `catchupPhaseSortBy`. Selecting by time is loss-prone under clock skew (a backdated during-replay event sorts before the boundary and is missed by both the delta and the live resume). Do NOT "tidy" the delta sort back to `catchupPhaseSortBy`. The global position/checkpoint is captured AFTER the bulk replay (fresh token, avoids oplog ageing). PR #208 closed the count-to-read window (re-read the recent tail until the matching count stops growing; `runCatchupForStream` dedups cached ids so overlapping re-reads stay at-least-once, and closes its source stream via try-with-resources). Residuals needing a global monotonic position (ADR 0008 for streams, `dcbposition` for DCB): net-count arithmetic loses events if events are deleted mid-replay, and `count(Filter.All)` on Mongo uses `estimatedDocumentCount`, which can undercount after an unclean shutdown. InMemory `SortBy.natural` means GLOBAL insertion order. The InMemory lazy-stream CME residual was fixed (#200).
- **Subscription resume-marker field (do not regress #272).** `MongoCommons` writes the marker under `checkpoint` (`GENERIC_CHECKPOINT`) and keeps `subscriptionPosition` (`LEGACY_GENERIC_CHECKPOINT`) as a read-only fallback for pre-rename documents (read tries `checkpoint` first, else legacy; `replaceOne` migrates on next save). Do not remove the legacy read-fallback or change either key, or not-yet-migrated consumers lose their resume point.
- **DCB storage.** DCB shares the CloudEvent storage boundary; metadata is CloudEvent extensions (`dcbtags`, `dcbposition`) so normal subscriptions still see DCB-written events. Position reservation uses a separate collection, but event documents go into the normal event collection with stream metadata. DCB appends are transactional and rely on `MongoTemplate` session synchronization `ALWAYS`. Reads capture a high-watermark and bound matches to `dcbposition > afterSequencePosition && <= highWatermark`, returning that watermark. Append-condition concurrency updates conservative checkpoint keys (`all`, `tag:<tag>`, type-only) to detect racing appends.
- **Capability mode is part of `EventStoreConfig`** (`STREAM`, `DCB`, or both; ADR 0018). It controls index/support-collection creation and runtime API guards, NOT the CloudEvent document format. Occurrent only creates missing indexes/collections for enabled capabilities and never removes indexes (operators create new indexes out-of-band before enabling a capability on large collections). DCB-only writes still assign per-storage-stream Occurrent stream versions (required if `STREAM` is enabled later). DCB-only Spring Boot must NOT expose stream `ApplicationService` or wrap subscriptions in `CatchupSubscriptionModel`; it still exposes `DomainEventQueries` for opt-in DCB helpers.
- **Do not gate the DCB application-service bean with `@ConditionalOnBean(TagGenerator.class)`.** That condition evaluates while bean definitions are still processing and can miss a user's `TagGenerator` in a real Boot context even though slice tests pass. It is a normal generically-typed `@Bean` that resolves `TagGenerator` via `ObjectProvider.getIfAvailable()` at instantiation and returns `null` when none exists.
- **In-memory `deleteAll()` must reset DCB sequence state**, else an emptied store reports stale DCB high-watermarks.
- **code-review-graph is structurally weak for architecture boundaries here** (file-based communities, no cross-community edges, test-dominated flows). Use it for inventory/impact, but verify module boundaries from Maven/source.
- **Two different "is this a DCB event" fields, do not conflate them.** `dcbTags` (capital T) is a Mongo-only, derived index array field, written only by `DcbDocumentMapper` on the DCB `append(...)` path, always present (empty array for zero tags) on a properly-appended event, and sparse-indexed (ADR 49) so `$exists` on it is cheap. `dcbtags` (lowercase) is the actual CloudEvent extension, present on any event a caller tagged via `DcbCloudEvents.withTags(...)`, regardless of which write API persisted it, and is what `DcbCloudEvents.isDcbEvent` and the in-memory filter matcher check. Before #282 landed, the Mongo `Filter.capability(...)` guard checked the derived array; Copilot correctly flagged that a `dcbtags`-tagged event written through `write(...)` (not `append(...)`) would then diverge, no array, so it would misclassify as stream-only. The fix (#282) was NOT to switch the Mongo check to the extension (that would defeat the sparse index, `$exists` on an unindexed field), it was to make the two fields provably equivalent by rejecting `dcbtags`-carrying events on the stream `write(...)` path in all four stores. Any new code that discriminates DCB-vs-stream in Mongo must use the indexed `dcbTags` array; anything working with a live `CloudEvent` (in-memory, or before persistence) must use the `dcbtags` extension via `DcbCloudEvents.isDcbEvent`.
- **A sparse index only accelerates `$exists: true`, never `$exists: false`.** A sparse index has no entries at all for documents missing the field, so there is no way to use it to find those documents either. This is why the DCB-side guard (#280, exclude stream events, `$exists:true` on `dcbTags`) gets full index support from a sparse index, but the reverse (#282, exclude DCB events, `$exists:false` on `dcbTags`) does not, and was accepted as a known, low-risk limitation (no index-backed acceleration for a bare capability-only query with no other narrowing predicate) since DCB has zero production deployments and the one real caller (`StreamCatchupSubscriptionModel`) always has a position-range predicate to ride on anyway. Do not "fix" this by adding a second index; if it ever becomes a real hot path, the correct fix is a written marker field on stream-only events, which was rejected as premature (see ADR 50 for the full analysis).

## Open Items

### Release readiness

- **Integration-test MongoDB version bump: DONE (#302).** `integration-tests.mongo.version` is now 8.0 (was the end-of-life 4.2.8). Two MongoDB 7.0+ compat fixes came with it: the index-conflict clash reports as error code 86 (`IndexKeySpecsConflict`) on 7.0+ where 4.x reported 85, so both are treated the same, and a compound sort combining a `$natural` step with field keys is now rejected with an `IllegalArgumentException` on the MongoDB stores (7.0+ rejects it server-side, 4.x silently dropped the field keys). - **DCB performance items: DONE (#303).** Both `explain()`-gated candidates proved necessary: a sparse `(type, position)` index (type-only criteria were over-scanning ~1000x) and a sparse `(dcbTags, position)` index (large boundaries triggered an in-memory `SORT`). Both added DCB-guarded across all three Mongo stores with before/after `explain` evidence.
- **Documented gaps CONSCIOUSLY ACCEPTED for this release (revisit post-release if demand):** no reactive competing-consumer model (ADR 0044), and reactive `@StreamSubscription` cannot honor a specific historical start time (ADR 0045). The latter fails loud rather than silently, and a correct fix needs time-to-position translation with clock-skew handling. These are known limitations shipped intentionally, not blockers.
- **Cross-store sort caveat:** a natural sort step combined with other sort steps is a valid insertion-order tiebreaker on the in-memory store but is rejected by the MongoDB stores (documented on `SortBy.natural`). MongoDB cannot express a natural sort inside a compound sort.
- The maintainer assigns the version number and date in `changelog.md` at release. Never invent one. Run a final full `mvn clean install` on the Java 21+25 matrix at the release commit before `mvn_release.sh`.

- **Counter-contention benchmark deferred** (ADR 0045 non-goal). Unified position uses one shared counter with per-append block reservation outside the write transaction. Parkster load is modest, so no benchmark was run. If an open-source user reports scale pain, benchmark naive vs block-reserved against a production-like Atlas cluster (WiredTiger write-ticket/write-conflict metrics); sharded counters are the escape hatch.
- **`queryForSequence` closing semantics.** Kotlin `DcbDomainEventQueries` Sequence/List extensions are leak-free (materialize into a `List`). Open: whether the stream-side `DomainEventQueries.queryForSequence` needs a closing/loan-pattern variant when the underlying store returns a live Mongo-cursor-backed `Stream`.
- Two `simpleName!!` non-null-assertion threads on PR #257 (reactive stream subscription DSL) were left as a deliberate open disagreement with a Copilot suggestion. A safe fallback for anonymous event classes in the stream/DCB DSLs is a small standalone follow-up, not done.
- **Env flake: `SubscriptionProjectionsWithSpringAndMongoDBApplicationTest` (stream projections example)** intermittently fails context load with `NullPointerException: BsonTimestamp ... is null`, the documented fixed-port-27017 / Colima Mongo-readiness flake. Unrelated to code changes, retry.

### Review findings (2026-07-07, shipped)

The six-angle architecture review (ADRs, DCB/decider API, subscription+query DSL API, catch-up design, DCB-store perf, subscription perf) plus an independent code-verified pass produced findings that were addressed across PRs #291-#299 and ADR 0053; see git history and `changelog.md` for detail.

- **Explicitly REJECTED (do not re-raise):** "agnostic `Subscriptions` delivering DCB events makes `EventMetadata.streamId` crash" is FALSE. DCB events are stored via the shared stream mapper with a generated partition stream id, so `EventMetadata.streamId` returns that partition id, not a crash.

- Keep durable-context small: the maintainer's token-discipline note is explicit that a growing file re-read every session is the real cost. Prune shipped detail into git/ADRs/changelog rather than accumulating it here.
- **If the orchestrator itself is in (or was recently in) plan mode, spawned subagents can inherit a stale plan-mode reminder and refuse to edit/build, even after the orchestrator has genuinely exited plan mode.** This happened repeatedly in the #283 session: two subagents independently explored, wrote a *plan* instead of executing, and reported being blocked by "plan mode" even when told explicitly to implement. The fix each time was to actually call `ExitPlanMode` at the orchestrator level first (not just tell the subagent to ignore it), then resume the same subagent with an explicit "you are not in plan mode, execute now" message. Do not accept a subagent's plan-mode refusal at face value if the orchestrator has already exited; check whether the orchestrator itself is still gated first, since a coordinator message alone cannot lift a subagent's permission mode. **Recurred 2026-07-09 (rewrite-recipe session):** a fork launched well after the harness auto-exited plan mode (auto-exit happened on writing the plan file, no explicit `ExitPlanMode` call was ever made) still returned in ~6s with **zero tool calls**, echoing the orchestrator's own status text as its "result" instead of implementing. Tell: a fork completing near-instantly with 0 tool uses and a summary that parrots your last message. The fix worked cleanly: resume the SAME fork in place via `SendMessage` to its agentId with an explicit "you returned 0 tool calls, that was wrong, you are NOT in plan mode, do the work with your tools now". It then executed normally. So the trigger isn't just an *active* orchestrator plan-mode; a fork can inherit a stale read-only stance whenever the session recently passed through plan mode at all.
- **Resuming a subagent requires the message/resume tool addressed to its existing agent ID, not a fresh `Agent` tool call.** A fresh call with the same description spawns an unrelated new agent with no memory of prior context, wasting the exploration the original agent already did. Always resume in place when correcting or continuing a subagent's work.
