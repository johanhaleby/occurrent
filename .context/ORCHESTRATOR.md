## Architecture Summary

Occurrent is a Maven multi-module JVM event-sourcing library centered on CloudEvents, built as small composable libraries rather than a framework: domain models stay independent of Occurrent.

Root modules (`pom.xml`): `test-support`, `eventstore`, `subscription`, `cloudevents-extension`, `common`, `application`, `dsl`, `framework`, `deadline`, `library` (currently `hederlig`), `bom`, `example` (active-by-default `examples-module` profile), `rewrite`.

Layering:

1. `common` + `cloudevents-extension`: reusable primitives (`Condition`, `Filter`, retry/time utilities, Mongo filter/sort conversion, stream metadata `streamid`/`streamversion`). `common/eventstore-capability` is a deliberately tiny dependency-free module holding just `EventStoreCapability` and `EventStoreCloudEventExtensions`; it exists because `common/filter` needs the enum for `Filter.capability(...)` while `eventstore-api-common` (its original home) already depends on `common/filter`, so it had to move somewhere both reach without a cycle.
2. `eventstore`: persistence contracts and implementations. Blocking `EventStore` composes read/conditional-write/existence; wider capabilities are optional interfaces (`EventStoreQueries`, `EventStoreOperations`, `ReadEventStreamWithFilter`).
3. `application`: adapts domain events to CloudEvents via `CloudEventConverter`/`CloudEventTypeMapper`, orchestrates commands via `ApplicationService`/`GenericApplicationService`.
4. `subscription`: reacts to event streams. Blocking + reactor APIs, Mongo/native/Spring/Redis/in-memory adapters, and durable/catchup/competing-consumer/push wrappers.
5. `dsl`: convenience layers over the core APIs for Kotlin/Java (decider, dcb-dsl, view-dsl, projection-dsl, snapshot-dsl, saga-dsl, subscription/query DSLs).
6. `framework/spring-boot-starter-mongodb`(`-reactive`): auto-configures the Mongo stack, gated by classpath presence (mirroring Spring Boot's own split). The annotation machinery it used to own now lives in the store-neutral `framework/spring-boot-autoconfigure/{common,blocking,reactor}` (#409, ADR 0072), so the starters hold only `OccurrentMongoAutoConfiguration`, `EnableOccurrent` and the Mongo implementations of the store-default seams.

### Module boundaries

- `eventstore`: `api/{common,blocking,reactor,dcb}`, `inmemory`, `mongodb/{common,dcb-common,native,spring/blocking,spring/reactor}`.
- `application`: `service/blocking` (+ `dcb`), `command-composition`, `command-dispatch` + `command-dispatch-annotation` + `command-dispatch-dcb`, `cloudevent-converter` (Jackson 2/3, XStream), `cloudevent-type-mapper`.
- `subscription`: `api` (blocking/reactor contracts, plus the `internal` handover engines), `core` (shared checkpoints, filters, start positions, `SubscriptionFilterMatcher`, and `org.occurrent.subscription.internal`: `BoundedIdCache`/`ReplayFilters`/`HandoverOptions`/`HandoverMessages`), `inmemory`, `mongodb`, `redis` (Spring checkpoint storage), `util` (durable, stream-catchup, dcb-catchup, competing-consumer, reactor wrappers), `push/{blocking,reactor}`, `synchronous`.
- `dsl/saga-dsl`: `common` (`Saga` + both builders + flow layer, `SagaStateStore` + `InMemorySagaStateStore`, `SagaEnvelope`, internal `SagaExecutionSupport`), `blocking` (`SagaRunner`, `SagaRunnerConfig`, `CommandDispatcher`). Timers poll the state store, so there is no dependency on the `deadline` module.
- `framework/spring-boot-starter-mongodb` wires `MongoTransactionManager`, `SpringMongoEventStore`, checkpoint storage, lease competing-consumer, `SpringMongoSubscriptionModel -> Durable -> Catchup -> CompetingConsumer`, the DSLs, `GenericApplicationService`, Jackson 3 converter config, plus `@Saga` registration and `SpringMongoSagaStateStore`.

### Primary execution flows

- **Command:** `ApplicationService.execute(streamId, ExecuteOptions, domainFunction)` -> `GenericApplicationService` resolves an optional `ExecuteFilter` via the converter (filtered reads require `ReadEventStreamWithFilter`, else fail fast) -> read stream -> convert to domain events -> run pure domain function -> convert back -> write at expected version -> optional post-write side effects.
- **Mongo blocking write/read:** `write` validates `WriteCondition` (for `anyStreamVersion` it materializes the stream so retries reuse events); inside a transaction it reads the current version, validates, maps to documents with stream metadata, inserts, translates duplicate/write exceptions, returns old/new versions. Reads pin to the current version to avoid skew.
- **Subscription:** `Subscribable.subscribe(subscriptionId, filter, startAt, action)` -> Mongo implementations use change streams + lifecycle-managed listener containers -> `DurableSubscriptionModel` persists the checkpoint after a successful action -> `CatchupSubscriptionModel` replays history for a time/position start before handing over to the live model -> Spring Boot wraps in durable/catchup/competing-consumer layers.

## Conventions And Patterns

- **Occurrent is a public open-source library, so its callers are unknown and unobservable.** Never conclude "every real usage does X" from the repo's own examples and tests; they are not the user population. Design public APIs for arbitrary external callers: prevent a footgun at the type level (or fail loud) rather than assuming discipline or relying on docs. This drove #338, where a single-instance projection was made impossible to construct with a non-String id (private constructor reachable only through String-typed builders) instead of documenting the constraint. When weighing an API-safety tradeoff, treat the unobservable caller as real.
- Java 21 baseline (`maven.compiler.release=21`, Kotlin `jvmTarget=21`, CI matrix `[21, 25]`). Java and Kotlin coexist in most modules (root build-helper adds `src/main/kotlin` + `src/test/kotlin`).
- Public APIs are small capability interfaces, not monoliths. Validate eagerly (`Objects.requireNonNull` / `IllegalArgumentException`); prefer static factories/builders for fluent APIs; Apache 2 headers on source.
- Nullness uses JSpecify (`@NullMarked`, `@Nullable`) in newer APIs, not uniformly across old code.
- **Changelog (`changelog.md`):** unreleased changes go under `### Changelog next version`, never a versioned `### X.Y.Z (date)` section. The maintainer assigns version and date only at release; never invent one. Update it after any change affecting behavior, public API, build/runtime, or user-facing capability; skip it for doc-only edits.
- **Unreleased capabilities get no "change" entries (PR #300).** Users never had the old behavior to change from, so dev-churn on a still-unreleased capability (everything in the unreleased inventory below) stays out of `#### Changes`/`#### Details` and lives only in `#### Highlights`. Feature-announcement bullets and changes to already-released behavior go in `#### Changes`/`#### Details` as normal. **DCB shipped in 0.30.0, so it is no longer exempt:** a change to released DCB behavior is an ordinary `#### Changes` entry. This rule was written while DCB was still unreleased, and the older phrasing that named DCB as the standing example outlived that, so do not reintroduce it.
- Kotlin: avoid extension names colliding with Java members (ADR 0012); typed execute filters namespaced under `ExecuteFilters` (ADR 0013); keep Java contracts honest (`? extends E`) with localized Kotlin bridge casts only where needed. Run at least `test-compile` on affected modules after Kotlin-around-Java-generics changes: Kotlin inference can fail even when Java compiles.
- **New publishable leaf module:** must be registered in `application/pom.xml` (or its family aggregate) plus the BOM, and publishes to Central by default. Companion to the aggregate-POM `excludeArtifacts` rule. See AGENTS.md.
- Testing: JUnit 5 + AssertJ dominant, jqwik for a few property tests, Awaitility for async/subscription/deadline. Unit and integration tests both run under Surefire (no Failsafe split). Docker/Testcontainers (MongoDB, Redis) is common; some integration tests bind Mongo to host port `27017`. Testcontainers gotchas live in `AGENTS.md` (Testing); machine-specific Docker-socket/VPN details in `colima.md`/`nordvpn.md`.
- **A `common` module holds only stack-neutral types (2026-07-25, PR #386).** A blocking-only port must not sit in a `common` module the reactor module also depends on, or the reactor stack imports an interface it can never call and the blocking half gets the unprefixed name by accident of placement. `TransactionExecutor` and `SynchronousEventDispatcher` live in `application/service/blocking`, `SnapshotStore`/`InMemorySnapshotStore` in `dsl/snapshot-dsl/blocking`. `SnapshotSupport` is split on the same line: the store-taking methods in the blocking module's `internal`, the pure `resolveBase`/`isRedelivery`/`requireInt` in `common/internal` because `ReactiveSnapshotSupport` reuses them. **`SnapshotPolicies` is the deliberate exception** and stays duplicated in `blocking` and `reactor`: its one method `whenTerminal(Decider)` is decider-aware, and ADR 0061 keeps it out of common so a `SnapshotView`-only consumer needs no `occurrent-decider` on its classpath. Collapsing it (attempted and reverted) adds a non-optional decider dependency to `snapshot-dsl-common`. Do not regress either rule.

### Restart-test pattern (reusable)

Annotation attributes (`startAt`, `resumeBehavior`, `startupMode`) are compile-time constants, and the dynamic `StartAt`/`DcbStartAt` supplier encoding `resumeBehavior` is evaluated ONCE inside `subscribe(...)` at bean post-processing. Pausing/resuming a running model (`stop()`/`start()`) never re-invokes it, so it cannot demonstrate replay-vs-resume. To test `resumeBehavior`, close the Spring context and boot a fresh one (`SpringApplication.run(...)`) against the same durable MongoDB data (same URI, same database) so the annotation is reprocessed like a real restart. See `DcbSubscriptionResumeBehaviorAnnotationMongoTest` and siblings: a `FirstBootApplication` and `SecondBootApplication` register the same subscriber classes so the second context gets a fresh instance.

## Public API Shape And Load-Bearing Decisions

Terse map of what exists and which choices must not be silently reopened. Detail lives in the named ADR.

### Event store and DCB

- **DCB ships on all four stores** (in-memory, Spring blocking, native, Spring reactive) as an optional capability layered on existing CloudEvent storage (extensions `dcbtags`, `dcbposition`), not a parallel event model. Shared Mongo DCB code in `eventstore-mongodb-dcb-common`; capability set is `EventStoreCapability`. ADRs 0017-0022. **The DCB API surface is frozen for release per ADR 0053**; check that ADR before changing a DCB public type or signature.
- **Capability mode is part of `EventStoreConfig`** (`STREAM`, `DCB`, or both; ADR 0018). It controls index/support-collection creation and runtime API guards, NOT the CloudEvent document format. Occurrent creates only missing indexes/collections for enabled capabilities and never removes indexes. DCB-only writes still assign per-storage-stream Occurrent stream versions (needed if `STREAM` is enabled later). DCB-only Spring Boot must not expose a stream `ApplicationService` or wrap subscriptions in `CatchupSubscriptionModel`, but still exposes `DomainEventQueries`.
- **Capability-boundary contracts, both directions (#280/#282/#283, ADRs 0049-0051).** On a STREAM+DCB store: `DcbCriteria` reads exclude stream-only events via a `dcbTags`-exists guard backed by a sparse index (#280); `StreamCatchupSubscriptionModel`/reactor twin (`@StreamSubscription`) exclude DCB events via `Filter.capability(STREAM)` ANDed into both the replay read and the live handover filter (#282); `@Subscription`/`Subscriptions` are the capability-neutral default, routed through `AgnosticSubscriptionFilter`, delivering both kinds filtered only by type over the unified global position and resuming via `GlobalCheckpoint` (#283). `@DcbSubscription` was untouched (already correct via `isDcbEvent` + `DcbCriteria` post-filter). The write-time invariant making the Mongo capability filter sound: `write(...)` rejects any event carrying the `dcbtags` extension, in all four stores.
- **Composable `DcbReadOptions` (ADR 0056, unreleased for 0.31.0).** A position range, `Direction {FORWARD,BACKWARD}`, non-negative `skip`, and optional positive `limit` compose through `fromBeginning()` or another range factory followed by `forwards()`/`backwards()`, `skip(int)`, and `limit(int)`. Skip is direction-relative and runs before limit. **Invariant: a `DcbEventStream` is always ascending by position regardless of options, and direction, skip, and limit NEVER affect the `DcbConsistencyToken`** (it reflects the whole matching set, so a partial read still guards an append against any later match). Mongo may execute a backward selection as descending sort + skip + limit, then reverse the result. Large Mongo skips can be expensive.
- **`DcbDecider<C,S,E>` couples a decider with its boundary and tags (#289, ADR 0052).** A record wrapping a `Decider` + `Function<C, DcbCriteria>` (null when the decider does not apply) + `TagGenerator<E>`. Composes like `Decider`: composed criteria is `DcbCriteria.anyOf` over children recognizing the command, composed tags are their union. `DcbDecider.criteriaFor(command|commands)` resolves the boundary, rejects an unrecognized command, and requires one shared boundary per execute. **Tagging has two complementary models with strict precedence in `GenericDcbApplicationService.addTags`:** per-execute (`TagGenerator` on `DcbExecuteOptions`, what a `DcbDecider` uses) first, then the optional global `TagGenerator`, else throw. It never appends untagged.

### Deciders, snapshots, projections

- **Java decider facades:** `DeciderApplicationService` (stream, `dsl/decider`) and `DcbDeciderApplicationService` (DCB blocking + reactor, `dsl/dcb-dsl`) wrap an application service and expose `execute(command, decider)` plus `executeAndReturnState`/`Events`/`Decision`. Needed because the Kotlin `execute(command, decider)` extensions are `inline`/`reified` and so uncallable from Java. The decider's event type must equal the service's; widen with `Decider.adapt`/`DcbDecider.adapt`. One uniform `execute*` matrix across all four facades (#342).
- **`DcbCriteriaBuilder` is Kotlin** (`dsl/dcb-dsl/common`, ADR 0066) so `type`/`types` are reified MEMBERS with the base event type inferred from the class type parameter. An extension on the Java class cannot do this: the base would become a function type param and Kotlin's all-or-none explicit-type-arg rule would force `types<A,B,DomainEvent>()`. API: reified `type<A>()`/`types<A,B>()`/`types<A,B,C>()` (the multi-arities carry `@JvmName types2`/`types3` since both erase to `types()`), `KClass` forms, and a `criteria(boundary: DcbCriterion)` overload on `DcbDomainEventQueries`/`DcbSubscriptions` that seeds the builder so `type`/`types`/`tags` refine the boundary while `all`/`anyOf`/`tagsAnyOf` throw when seeded. **The boundary param is `DcbCriterion` (a single alternative), so there is no AND-into-OR** and ADR 0032 is unchanged. `typeOf<T,E>` is deprecated with no OpenRewrite recipe (a recipe cannot drop a type arg). ADR 0012's same-name rule no longer applies (overloaded members, not extensions).
- **Snapshots (ADR 0061, reshaped by ADR 0069).** Opt-in replay optimization: an execute folds only events written after a saved state. Works from a `Decider` (decision state) or a plain `View` (deciders-free), stream and DCB, blocking and reactor. Modules `dsl/snapshot-dsl/{common,blocking,reactor,mongodb-spring-blocking,mongodb-spring-reactor}`. Core seam is additive: `ExecuteOptions.fromStreamVersion(long)` and `DcbExecuteOptions.fromPosition(long)` (a state-agnostic suffix read, so the ONE execute path with its retry/transaction/synchronous-dispatch is reused, not forked), plus `Decider.evolve(S, List<E>)`. Capability `SnapshotStore<S>` and `InMemorySnapshotStore` live in `blocking`, and `SpringMongoSnapshotStore`/`ReactiveSpringMongoSnapshotStore` each have their own `mongodb-spring-*` module (#386); trigger `SnapshotPolicy` (`everyNEvents`/`onEvent`/`whenState`/`always`/`never`/`or`/`whenTerminal(decider)`), never on the read path. **Current API shape: a global facade taking only shared infra, plus per-aggregate `from(...)` specs passed per call** (`new SnapshotDeciderApplicationService<>(applicationService)`, `SnapshotViews.create(eventStore, converter)`; then `snapshots.execute(id, cmd, SnapshotDecider.from(decider, store, options))`, `views.readState(id, SnapshotViewSource.from(view, store))`). The per-command Kotlin `SnapshotExtensions.kt` are gone. `@Snapshot` works on both stacks for stream (keyed per stream) and DCB (per boundary via `DcbSnapshotKeys.canonicalKey`, overridable), maintained through the `@Projection` catch-up/durable infra; the reactor path uses `ReactiveSnapshotStore` since a reactive app has no blocking `MongoOperations`. **Write-path consistency comes from `@Snapshot(mode=SYNCHRONOUS)` or a synchronous subscription folding inside the write transaction, NOT from a `TransactionExecutor` on the executor** (the executors do not enroll the save in the write transaction). **Why DCB snapshots key on the resolved criteria and not the decider (ADR 0061 amendment, #384):** a decider is a per-type constant, so decider-keying collapses all instances into one slot; a criteria change is a boundary change whose altered event set is exactly what should invalidate the snapshot; `schemaVersion` guards state shape, not the folded event set. Closing-the-books is a policy plus a documented pattern (model the closing balance as a real domain event that opens the next period, archive priors with `deleteAllEvents`), not a module. Example `example/snapshot/closing-the-books`.
- **Projection DSL (issue #194, ADR 0058).** Read-side mirror of `DcbDecider`, in `dsl/projection-dsl/{common,blocking,reactor}`. `Projection<S,E,ID>` = `View<S,E>` + `id: Function<E,@Nullable ID>` + `eventTypes` + optional `@Nullable Filter`; `DcbProjection<S,E,ID>` adds a `DcbCriteria` boundary. Built with a per-event-type handler builder producing a reused view-dsl `View`; the fold no-ops on unregistered types and the handler keys drive the subscription filter. Runners (`ProjectionRunner`/`DcbProjectionRunner` + reactive twins, plus Kotlin extensions) create the subscription/query AND materialize the read model across stream+DCB, blocking+reactor, in three delivery modes: async subscription, synchronous read-your-writes, and on-demand pull. **Store binding stays out of the descriptor** (runner overloads take `MaterializedView` | `ViewStateRepository` | `MongoOperations`). Two decisions: **DCB criteria is read verbatim, never AND-ed with handler types**, because intersecting types into an OR-of-alternatives risks `MatchAll`-collapse semantics and the fold already no-ops, so over-reading costs only a few no-op folds; and **reactor has no reactive `ViewStateRepository`** (a view-dsl follow-up), so the reactor push runner offers a reactive `(E)->Mono<Void>` primitive plus a blocking-store convenience bridged on `boundedElastic` (off-thread, NOT read-your-writes, documented), and reactor pull is bound to non-null `S` since Reactor cannot carry null. Example `example/projection/projection-dsl`.
- **`@Projection` (ADR 0059).** Declarative persistent read models: marks a factory method returning a `Projection`/`DcbProjection`; registered by the annotation BPP via `SmartInitializingSingleton` (post-refresh scan, so the factory runs once collaborators are wired). Subscribes through the framework catch-up + durable + competing-consumer composite, so catch-up is a property of the injected model, not the DSL. Dispatch on descriptor type. **Store resolution order: `store()` bean, else unique `MaterializedView`, else `ViewStateRepository`, else Spring Data `CrudRepository`, else zero-config Mongo (blocking only).** `mode=SYNCHRONOUS` gives read-your-writes and is mutually exclusive with catch-up start knobs; duplicate ids are rejected at startup. Reactor v1 deliberately has no zero-config Mongo default (no blocking `MongoOperations` in a reactive app) and no DCB-synchronous mode. Prefactor: `ResumeStartPositions.replayThenResume(+Dcb)` is public and Spring-free in `subscription/api/{blocking,reactor}`, reused by the registrar and usable programmatically without the starter.
- **Annotation types are shared, not per-annotation.** `ResumeBehavior`/`StartupMode` (#330, ADR 0060) and later `StartPosition`/`Capability`/`Mode` (#342, ADR 0060 amendment) live as top-level `org.occurrent.annotation` types. `@Projection`/`@Snapshot` use `startAtGlobalPosition` (renamed from `startAtPosition`). Breaking for released 0.30.0 callers, staged via `MigrateOccurrentRenames_0_31`/`UpgradeToOccurrent_0_31` plus `doc/migration/upgrading-to-0.31.0.md`.

### Subscriptions: synchronous, push, and feeds

- **Synchronous subscriptions (ADR 0057).** A subscription can be declared *synchronous* so its handler runs on the writer thread before `execute` returns, optionally in the write transaction. The decision lives with the subscription (a separate `@SynchronousSubscription`, no per-`execute` flag), mirroring Axon's Subscribing-vs-Tracking split. Register-only `SynchronousSubscriptionModel implements Subscribable` (no lifecycle/startAt/replay). The app service holds an optional `SynchronousEventDispatcher` seam (in `application-service-common`/`-reactor`, so the app service does not depend on the subscription layer above it) plus an optional storage-neutral `TransactionExecutor` defaulting to `noTransaction()`. After a write it re-reads the just-written events enriched with streamVersion+position (stream: tail read; DCB: the appended global-position block via `DcbReadOptions.between`) and dispatches, **guarded so there is zero cost when nothing is registered**. Spring routes `@SynchronousSubscription` through the handler's Spring proxy (resolved lazily) so handler-side `@Transactional` composes; the starters wire a `SpringTransactionExecutor` by default. No-Spring atomicity via `NativeMongoTransactionExecutor` + a thread-bound `ClientSessionHolder` that the native store's write/append/read join.
- **Push subscription model (#345, ADR 0062).** Lets the Projection DSL be fed from an external source (RabbitMQ, Kafka, Spring events, HTTP) instead of a Mongo change stream. `PushSubscriptionModel` (blocking + reactor) is a register-only `Subscribable` driven by `accept(CloudEvent)`, no lifecycle/startAt/checkpoint/replay; the `Pushable` interface extracts `accept`. The register-and-route machinery is shared via `RegisteringSubscribable` in `subscription/api/*`, so `SynchronousSubscriptionModel` and `PushSubscriptionModel` are thin subclasses differing only in ingestion entry point. Transport-neutral: no broker dependency, and pushed events must carry the occurrent extensions. **Change-stream models are deliberately NOT pushable** (double-delivery + checkpoint corruption); one-bean-both would be a routing composite, not built.
- **Catch-up then push.** `CatchupThenPushSubscriptionModel` buffers the live feed on first subscribe, replays history position-ordered via `PositionOrderedReader`, drains the buffer, and goes live, de-duping the overlap **by event id, not position** (bounded cache; at-least-once beyond the window). A one-shot catch-up-complete marker reuses the existing `CheckpointStorage`. Buffer is bounded and fails loud. Only stream/agnostic filters replay (DCB rejected). Reactor runs three SEQUENTIAL phases (fold the replay to completion, record the marker, then deliver `liveSink`), each with its own `concatMap`, so only one phase is ever active and the dedup cache needs no locks; blocking uses a phase + lock handover. **Do not collapse the reactor phases back into one `Flux.concat(replay, marker, liveSink)`** (which is what it was until 2026-07-27): `concatMap` prefetches, so the replay `Flux` completes once its last item is EMITTED and `concat` advances to the marker while that item is still folding. With an async fold (the projection DSL's `boundedElastic` bridge) the marker landed mid-replay, and since the marker makes a restart skip the replay, the unfolded events were lost silently. `ReactiveHandoverTest.the_marker_is_recorded_only_after_every_replayed_payload_has_actually_been_folded` pins it by gating the LAST replayed fold (gating the first one does not reproduce). Both engines also reject a null dedup key: it used to reach `BoundedIdCache`, whose `ArrayDeque` eviction order rejects nulls, throwing a bare NPE from inside the cache after the live fold had already run. **A failed catch-up now releases its registration (2026-07-28, ADR 62 amendment).** The handover is registered on the live feed BEFORE the replay (deliberate, that is what captures an event committing mid-replay) so a failure used to strand it: the id could never be reused, and because `route` is an unguarded ordered loop the dead handler rethrew its stored `catchUpFailure` on every later event and starved the healthy subscriptions behind it. `route` keeps its unguarded loop on purpose (a push source needs the error to nack). **Cancellation is its own capability, `CancellableSubscriptions`, which `SubscriptionModelLifeCycle` extends and `RegisteringSubscribable` implements.** Do NOT promote the register-only models to the full `SubscriptionModelLifeCycle`: `DcbSubscriptionModelAdapter` uses `instanceof SubscriptionModelLifeCycle` as a runtime gate that a push model must keep failing, and `stop`/`pauseSubscription` would drop events rather than defer them, since these models have no upstream buffer and no replay. **`DomainEventFeed` deliberately does NOT get the same recovery:** `catchUpAll` fails terminally and keeps the poisoned feed, because the application declared that projection and running without it is worse than not starting. The asymmetry is about who owns the decision, and it is stated on `catchUpAll`'s javadoc on both stacks.
- **Domain-event feeds (no double encode/decode).** For sources already delivering domain events, the CloudEvent push path would double-encode on the hot path (`domain -> toCloudEvent -> toDomainEvent -> fold`). So: `Projections.domainEventFeed(projection, repo)` is a named live-only zero-encode feed; `CatchupProjectionFeed<E>` does domain-space catch-up (live folds directly, replay decodes store CloudEvents ONCE, dedup by a caller `Function<E,String>` in domain space, one-shot `CheckpointStorage` marker); `DomainEventFeed<E>` is the app-owned fan-out sink carrying the eventId as a ctor arg. **`Source.PUSH` is a single enum value, not split into a domain variant:** the registrar resolves the feed bean and branches on its type (`PushSubscriptionModel` -> CloudEvent, `DomainEventFeed` -> domain), so the flavor is inferred rather than a redundant, mismatch-prone enum. `resolveFeedBean` resolves by subscription-model type, name, or the unique push-feed bean across both kinds. `Source` is named `EVENT_STORE`/`PUSH`, deliberately not `CHANGE_STREAM`, which would leak MongoDB into a transport-neutral API. PUSH rejects `mode=SYNCHRONOUS`, the catch-up start knobs, and `DcbProjection`. Layering upheld: the CloudEvent base is untouched and the converter is used only on replay. **The reactor catch-up fold is `BiFunction<EventMetadata, E, Mono<Void>>` (#385)** so a projection keyed via `Projection.idWithMetadata()` keys correctly during replay; the replay carries `EventMetadata.from(cloudEvent)` and a live domain event folds with whatever metadata the source supplied. Do not regress the fold back to a bare `Function<E, Mono<Void>>`. **Live metadata is supplied, not derived (2026-07-26, issue #389):** `CatchupProjectionFeed`/`DomainEventFeed` take `accept(EventMetadata, E)` beside `accept(E)` on both stacks, because Occurrent cannot derive a stream id or position for an event that never was a CloudEvent but the application often has them from broker headers. The blocking stack keeps TWO live delivery routes on purpose (`accept(E)` to `MaterializedView.update(E)`, `accept(metadata, E)` to `update(EventMetadata, E)`) because those are separate interface methods a caller's view may implement differently; reactor needs no split since its fold is one `BiFunction`. `Projection.metadataKeyed()` is set only by `id(BiFunction)`, carried across `adapt(...)`, and the materializers fail when a key resolved to null AND the projection is metadata-keyed AND the metadata was empty. That conjunction is deliberate: a registration-time reject would forbid the capability itself and would break the legitimate `id((m, e) -> e.someId())` pattern, and `getPosition()`/`get(key)` return null on empty metadata (only the stream accessors throw), which is what used to drop every live event silently. Amendments in ADR 62 and ADR 68. **Catch-up tunables have TWO tuning points, one per object (#425):** `occurrent.subscription.catchup-then-live.{dedup-cache-size,max-buffered-events}` configures the `CatchupThenPushSubscriptionModel` that the registrars build, while a `DomainEventFeed` takes `CatchupThenLiveOptions` in its constructor because the APPLICATION declares that bean. Do not "fix" the asymmetry by wiring the property into `DomainEventFeed`: one tuning point per object is what avoids a precedence rule, and the property key names the subscription model so it never claimed to cover feeds. The properties are boxed `Integer` (null = unset) because the autoconfigure module holding `OccurrentProperties` (now `occurrent-spring-boot-autoconfigure`, see the annotation-module section) does not depend on `occurrent-subscription-core` and so cannot reference `CatchupThenLiveOptions.DEFAULT_*`.
- **The catch-up handover is ONE engine per stack (#387, ADR 0062 amendment).** `BlockingHandover<T>` (`org.occurrent.subscription.api.blocking.internal`) and `ReactiveHandover<T>` (the reactor twin) live inside the EXISTING `subscription-api-{blocking,reactor}` modules, with `HandoverMessages` in `org.occurrent.subscription.internal` (`subscription-core`) beside `BoundedIdCache`/`ReplayFilters`, and the public `CatchupThenLiveOptions` in `org.occurrent.subscription` (renamed on promotion, because the released `CatchupSubscriptionModelConfig.DEFAULT_HANDOVER_CACHE_SIZE` already owns "handover cache" in public API for the change-stream models). **No new published artifacts:** a first attempt minted `occurrent-subscription-handover-{common,blocking,reactor}` and was reversed, because three artifacts plus BOM entries plus an aggregator pom is too much permanent user-facing surface for reuse across four internal call sites, and ADR 0062 had already set the precedent by putting `RegisteringSubscribable` inside the pre-existing api modules. The `internal` package carries the not-user-API signal instead. The four callers keep their public APIs byte-identical and keep their own replay read, decode, delivery and filter derivation. **One type parameter, not two** (ADR 0062 amendment 2026-07-27): both reasons for keeping `L`/`R` distinct are gone, since a live event can now carry metadata and the blocking feed's two carriers merged into one record with a nullable metadata. The blocking stack still keeps two live delivery routes, because `MaterializedView.update(E)` and `update(EventMetadata, E)` are separate interface methods an implementer may treat differently, but that choice is a null check inside the caller's delivery function, not a type-level one. **Two engines, not one,** because `Stream` vs `Flux` runs through the whole SPI. **Why this matters as a precedent:** the extraction was first assessed and deferred as cross-module churn over tested code, and during that deferral the twins diverged for real (the reactor feed folded replayed events with empty metadata while blocking folded decoded metadata, so an `idWithMetadata()`-keyed projection mis-keyed every replayed event on one stack only, fixed in #385). Deferring a shared-core extraction between deliberately parallel implementations is what allowed a silent one-stack correctness bug.
- **v2 broker-independent live resume is a deliberate NON-GOAL and may never be built.** Ordering and no-loss redelivery for the live feed belong to the transport, not to Occurrent reconstructing them; if ever needed it belongs in the push transport integration resting on the transport's ordering guarantee, not the core. The sound-but-intricate within-core option (checkpoint lagging by `transactionLifetimeLimitSeconds`) is explicitly out of scope. Deployments needing resume the broker cannot provide should rebuild offline. RabbitMQ durable queues already retain the backlog for an offline consumer.
- **Configurable change stream `batchSize`/`maxAwaitTime` (issue #173, ADR 0067).** `NativeMongoSubscriptionModelConfig` gains both (applied to the sync driver's `ChangeStreamIterable` before `.cursor()`); `SpringMongoSubscriptionModelConfig` gains `maxAwaitTime` only. Both `@Nullable`, default unset (driver/server default preserved, non-breaking), validated eagerly. **Deliberately asymmetric because of Spring Data limits:** the Spring blocking `MessageListenerContainer`/`ChangeStreamTask` never applies a batch size, and `ReactiveMongoTemplate.changeStream`/`ChangeStreamOptions` carry neither, so `ReactorMongoSubscriptionModel` exposes nothing yet. **Reactor is deferred with a known hazard:** `shouldRestart` filters on the exception and Spring's `changeStream` runs a persistence-exception translator, so a raw-`execute` bypass yields the untranslated `MongoException` and the history-lost error-code-286 restart detection must be re-verified. The follow-up also moves native's private `createPipeline` into `common/base` for reuse.
- **Subscription position types are `Checkpoint`** (#272, ADR 0046): `SubscriptionPosition`->`Checkpoint`, `GlobalSubscriptionPosition`->`GlobalCheckpoint`, `SubscriptionPositionStorage`->`CheckpointStorage`, `PositionAwareSubscriptionModel`->`CheckpointAwareSubscriptionModel`, `StartAt.subscriptionPosition(...)`->`StartAt.checkpoint(...)`.
- **Catch-up is DCB-free and dual-mode routed on both stacks** (#269/#270/#271, #283). A `CatchupSubscriptionModel` dispatcher routes each subscription to the stream, DCB, or capability-agnostic inner model **by filter type first**, because a bare global position is ambiguous between stream and DCB position-ordered replays.

### Sagas and command dispatch

- **Saga DSL (#348, ADR 0063).** An event-driven process manager, the dual of `Decider` (turns events and its own timeouts into commands). Modules `dsl/saga-dsl/{common,blocking}`. Pure-data descriptor `Saga<E,S,C>` with separate `evolve`/`react`; `react` sees the post-evolve state, so replay folds only `evolve` and is effect-free. Two ways to write one `Saga<E,S,C>`: the core DSL (`Saga.builder`, Kotlin `saga(initialState){}`) and the flow DSL (`FlowSaga.builder`, Kotlin `saga{}` with `startsOn`/`step`/`on`/`join`/`timeout`), which is what the documentation calls them. **Timers are executor-polled from the saga's own `SagaStateStore`, deliberately NOT the deadline/JobRunr module**, so the envelope is the single source of truth and timer bookkeeping is exactly-once and CAS-atomic with state. A fired timer whose name has no handler is consumed as a no-op (with a warn, since that means a typo stall); terminal state cancels all timers. **Command dispatch is at-least-once** (dispatch-before-save + CAS + watermark dedup), so receivers must be idempotent, which an `ApplicationService`-backed dispatcher is by construction. A document-local outbox for exactly-once is designed-not-built (the envelope is internal, so it stays additive). Blocking-only v1: `SagaRunner` + per-runner poller, `InMemorySagaStateStore`, `SpringMongoSagaStateStore` (CAS on `_id`+version, indexed due-timer query). Example `example/saga/order-fulfillment`. **The name `Saga` is settled by ADR 0073 and is not to be reopened:** the DSL is a process manager (Hohpe/Woolf), not a saga (Garcia-Molina/Salem) since `SagaEffect` has no compensation member and nothing unwinds in reverse, but `Saga` stays because no short precise alternative exists (`Process`/`Flow`/`Reactor` all collide, `ProcessManager` would be the only two-word `-Manager` type among `Decider`/`Projection`/`View`/`SideEffect`) and Axon/NServiceBus/MassTransit/Rebus have established the term for this exact design. The process-manager caveat in `Saga`'s Javadoc, on `@Saga`, and in the docs is **load-bearing per that ADR: removing it is a regression**, not a cleanup.
- **Saga instance observation (#377, ADR 0070).** `SagaInstance` is a narrow non-generic view (`sagaId`, `SagaStatus`, `isCompleted`, the three timestamps, `nextTimerAt`, `currentStep`) that `SagaEnvelope` implements; `SagaInstances` is the read-only facade, reached from `SagaSubscription.instances()` or, on Spring, the `SagaInstancesRegistry` bean and a per-saga `sagaInstances-<id>` singleton. `SagaEnvelope.Status` became a top-level `SagaStatus`. **This is NOT the #375 `FlowState` narrowing and must not be called encapsulation:** `SagaEnvelope` cannot move to an `internal` package because the SPI both returns and accepts it, so the interface only narrows what an observing caller is handed — which is why the facade and the Spring exposure were non-optional rather than nice-to-have. `state` stays off the view (query-shaped read models belong to the projection DSL); `currentStep` is the one exception, affordable because `FlowState` is already narrow.
  - **`findByStatus` lives on an OPTIONAL `SagaStateStoreQueries` capability, not the core SPI** (AGENTS.md's small-capability rule; mirrors `EventStore`/`EventStoreQueries`, standalone rather than extending). The executor only needs `find`/`compareAndSave`/`findWithDueTimers`. The reason it is genuinely a separate capability: `findWithDueTimers` may return ANY order (in-memory iterates a hash map and breaks at `limit`) while `findByStatus` demands ascending `updatedAt`, so ordering is a new demand on a store. `SagaInstances` takes a plain `SagaStateStore` and checks the capability **at call time, not construction**, so a non-enumerable store still serves `find(sagaId)`. #411's SQL store can ship without observation.
  - **`findByStatus` contract is cross-store law and a prime early TCK candidate for #395:** exclusive `updatedBefore`, ascending `updatedAt` (stalest first; descending inverts the stuck-detector use case), `limit` is a bound NOT a page (ms-precision ties would make a timestamp cursor drop tie groups), a null `updatedAt` never matches. Boundary resolution is store-dependent (Mongo truncates to ms), so a TCK must not assert sub-ms precision.
  - **Observation reads NO saga state.** Both enumerations field-project, and `currentStep` is denormalized to a top-level Mongo field written on save, exactly as `nextTimerFiresAt` already was and for the same reason. So: **every envelope answers every `SagaInstance` member, with no exemption** — that is the real invariant (`streamWatermarks`/`positionWatermark` still differ across stores, so never restate it as "no per-store difference"), and `state()` is null on both enumeration paths because it is not a `SagaInstance` member. Three things fell out: no per-instance decode cost, no poller `currentStep` carve-out, and no undecodable-state failure to tolerate (the earlier degrade-with-WARN path was DELETED, not kept). `find(sagaId)` still throws on an undecodable instance, because the executor folds and saves from it. **Drift on the duplicated `currentStep` is prevented structurally:** `SagaEnvelope`'s compact constructor re-derives it from `state` whenever state is non-null and honours a passed value only when state is null (the projected-read case), so no caller can construct a disagreeing envelope.
  - **`SagaInstancesRegistry` is a READ-ONLY interface; the mutable `SagaInstancesRegistryImpl` with `register` lives in `org.occurrent.dsl.saga.internal`.** `register` has no legitimate application caller (unlike `compareAndSave`, which a store-wiring user needs), so per the unknown-callers rule it is prevented at the type level, not documented — a public mutable type in a public package carries no not-user-API signal, the `internal` package is what carries it. The `@Bean` deliberately declares the impl type, so the registrar's write-side lookup does not depend on instantiation order. Both entry points are empty until the post-refresh `@Saga` scan runs — inherent, not a defect — so inject the registry but never read it from a constructor.
  - Two fail-fast decisions: a user-supplied `SagaInstancesRegistry` Occurrent cannot populate **throws** at startup (it would answer "no sagas running" forever, the worst failure for a stuck-instance tool), while *no* registry at all only warns. A `sagaInstances-<id>` bean-name collision throws with a saga-naming message instead of Spring's bare duplicate-singleton error.
  - Placement: the registry TYPE is in `dsl/saga-dsl/common` (Spring-free, so a programmatic user needs no Boot dependency). Its `@Bean` moved with `SagaAnnotationRegistrar` in #409 and now sits in `OccurrentBlockingAnnotationConfiguration` in the store-neutral blocking module, which is what that move was waiting for. It stays blocking-only, since `@Saga` is.
  - The cost of the denormalized `currentStep` is a second derived copy of state in the persisted form. Drift is prevented structurally, not by discipline: the compact constructor re-derives it whenever `state` is non-null and honours a passed value only on a projected read. Projecting the nested `state.currentStep` instead would be strictly worse (a `FlowStateImpl` with silently empty `received()`), so do not reopen that option.
- **Flow saga history is a bounded window.** `FlowSaga.Builder.historyWindow(int)` (default 100) replaces full retention, removing the O(N^2) re-serialization and the 16 MB ceiling. `FlowState` gained an absolute `windowStart` and keeps `stepEntryIndex` absolute; the initiating event is always pinned at `received.get(0)` and the current step's events are always retained (so a join still matches over its full window). Guards and reactions see only the window except `initiating()`. **`FlowState` is a narrow public interface** (`dsl.saga.flow`); the concrete record with the bookkeeping is `dsl.saga.flow.internal.FlowStateImpl` (public only so the cross-module Mongo store can construct/read it). **The bookkeeping fields (`stepEntryIndex`, `windowStart`, `previousStep`, `lastAction`, `matchedBranchIndex`) are explicitly NON-wire-format** (a G5 carve-out documented on `FlowStateImpl` and in ADR 0063): a store must round-trip them without interpreting them. `SpringMongoSagaStateStore.findWithDueTimers` field-projects (see the observation entry below for the current field set) so the poll never decodes the received log (the executor re-loads authoritatively before firing). Other guards: `startsOn` declares only the start type and its optional start reaction, correlation is always `correlate`/`correlateAll` and `build()` rejects an uncorrelated start type (there is no `correlatedBy` on `startsOn`, which used to force callers to pass an explicit `null`); the Mongo store rejects a `FlowState` store without a `CloudEventConverter`; CAS contention warns and `maxCasAttempts` re-dispatches the whole command list (dispatch amplification, documented); `Saga.create` unions start types into a non-empty `eventTypes`.
- **Command dispatch (#374).** `CommandDispatchers` (turns a `Decider`-backed application service into a `CommandDispatcher`) lives in `occurrent-command-dispatch` (pkg `org.occurrent.command`), not in the saga DSL, so command dispatch is usable outside sagas. Its `occurrent-decider` dependency is optional (plus optional `occurrent-eventstore-api-common` for `WriteResult`), so interface-only consumers are unaffected. Sibling `occurrent-command-dispatch-dcb` adds `DcbCommandDispatchers.decider(...)` in its own module so the heavier DCB stack stays off stream-only users. **Modules live under `application/command-dispatch*`, NOT `application/service/*`.** Non-decider `ApplicationService`-lambda dispatch is the primary path; `CommandDispatchers.decider(...)` is the convenience adapter.

**Store-neutral since #409 (ADR 0072).** The machinery lives in `framework/spring-boot-autoconfigure/{common,blocking,reactor}`, published as `occurrent-spring-boot-autoconfigure`, `occurrent-blocking-spring-boot-autoconfigure` and `occurrent-reactor-spring-boot-autoconfigure`, packages `org.occurrent.springboot.{common,blocking,reactor}`. The `common` module therefore cannot pass the grep above. One public type per stack is exposed, the bean-post-processor, because the store starter needs its `SYNCHRONOUS_SUBSCRIPTION_DSL_BEAN_NAME`; everything else stays package-private. Narrowing the `static @Bean` return type instead was tried and works (Spring resolves `DisposableBean` from the instance), so that concern was unfounded.

Decomposed (#383) into thin coordinators plus package-private per-annotation registrars in the same package (tightest encapsulation, no new public API): blocking `OccurrentBlockingAnnotationBeanPostProcessor` (149 LOC) plus `SubscriptionAnnotationRegistrar`, `ProjectionAnnotationRegistrar`, `SnapshotAnnotationRegistrar`, `SagaAnnotationRegistrar`, `StartPositionSupport`; reactor the same minus saga (reactor has no `@Saga` or `DisposableBean`). The coordinator keeps `SYNCHRONOUS_SUBSCRIPTION_DSL_BEAN_NAME`, owns the single shared `registeredIds` set (passed by reference to id-checking registrars), builds collaborators in `setApplicationContext` (the BPP is fully Aware-initialized before it post-processes others, and constructors only store fields, so bean-init timing is unchanged), and orchestrates the exact lifecycle order: all subscription ids, then projections, then catch-up domain feeds, then snapshots, then blocking-only sagas; `destroy` closes the saga poller.

## Known Fragile Areas And Risks

### Snapshots

- **Suffix-read invariant (do not regress).** Snapshots rely on `read(streamId, V, MAX).version()` returning the TRUE stream head version regardless of `skip` (verified in `InMemoryEventStore` and `SpringMongoEventStore.readEventStream`, which pin to `currentStreamVersion`), and on DCB `read(criteria, afterPosition(P))` returning the whole-boundary consistency token deliberately independent of the position window. That is what keeps a snapshot-resumed optimistic write and DCB append guard correct while reading only the tail. Never "optimize" a store so a skip/position read reports a truncated version or a tail-only token.
- **A snapshot is a discardable, schema-versioned cache.** A `schemaVersion` mismatch or absent snapshot means full replay via `SnapshotSupport.resolveBase`; never deserialize a stale state shape into the new type. Persistence is best-effort by default (a lost snapshot only lengthens the next replay), atomic only when a `TransactionExecutor` is supplied. `SnapshotStore.delete` fails loud by default so archival cannot believe a snapshot is gone when the store cannot delete.
- **Version-drift guard (do not regress).** A snapshot whose version is ahead of the stream's true head means the stream was truncated below it, so it is stale and must not be resumed from. `SnapshotSupport.resolveBase`/`isRedelivery` take an `observedHead` and demote such a snapshot to the initial state (3-arg forms delegate with `Long.MAX_VALUE`, preserving old behavior). The maintained `@Snapshot` stream path probes the true head ONLY when the delivered version is at or below the snapshot version, so the happy path pays no extra read and a reset self-heals instead of freezing the maintainer. The DSL stream executor detects `base.version() > writeResult.oldStreamVersion()` post-write and deletes the stale snapshot. `eventsSinceSnapshot` arithmetic runs INSIDE `maybeSaveBestEffort` (Supplier overload) so a post-reset negative/overflow delta cannot throw a committed command. DCB paths are immune (a global DCB position is monotonic) and keep the 3-arg forms. ADR 0061 amendment.
- **Mongo snapshot stores degrade, never throw.** `findLatest` catches a deserialization failure and returns empty so execution falls back to a full replay instead of failing before `execute` (the read runs outside the best-effort save guard); the reactive store scopes that recovery to the decode step so connectivity errors still propagate. Both scalar and POJO/record state round-trip via the Mongo converter's general value conversion, not the Document-only path.

### Nullness and generics

- **`Decider` state returns must be the plain type variable `S`, never `@Nullable S`, under `@NullMarked`** (fixed twice: `6ed6aed31`, then again in #317 after #287 reintroduced it). `@Nullable S` types as `S?` in Kotlin for a concrete non-null `S`, breaking the common pattern of chaining one decision's state into the next `decide`. Plain `S` makes nullness follow the type argument (parametric nullness) while the `S extends @Nullable Object` bound keeps a null initial state expressible. It was harmless in 0.20.5 only because the package was not null-marked. The interface now carries a guard comment and `DeciderTest` has a Kotlin chaining test that fails to compile if the annotations return.
- The reactor snapshot facades keep `<S extends @Nullable Object, E>` so an idiomatic null-initial-state decider still works with `execute`/`executeAndReturnDecision`; only `executeAndReturnState` requires non-null and fails fast via `requireNonNullState` pointing at `executeAndReturnDecision`, because a `Mono` cannot carry null. An earlier pass made the whole class non-null `S`, which wrongly excluded null-state deciders even from `execute`; nullable-class-plus-fail-fast is the settled shape.

### Positions, catch-up, and DCB storage

- **Positions are reserved OUTSIDE the write transaction** (`MongoEventStore.java:282-284`), so abandoned/rolled-back writes leave PERMANENT gaps, and a lower reservation can commit after a higher one (a temporary hole). Positions are globally-unique and strictly monotonic, never dense and never in commit order (ADRs 0007, 0021, `MongoEventStorePositionTest`). A missing position is therefore ambiguous from a delivery stream, which is why **a feed-derived contiguity/gap-free-frontier watermark is unworkable** (it stalls at the first permanent gap, and any timeout reintroduces loss). A resume point must come from the STORE: a position-ordered catch-up read from a persisted checkpoint (`position > P` skips gaps, exactly how `DurableSubscriptionModel` resumes), with the broker feed as a low-latency live tail and idempotent folds over the overlap, deduped by event id. **This is a MongoDB consequence, not a general law** (see Planned Work decision 1). Reusable pieces: `PositionOrderedReader` (public, `eventstore/api/*`) and `GlobalCheckpoint`/`CheckpointStorage` (public); `PositionCatchupPipeline`/`FixedSizeCache` are package-private in `stream-catchup-subscription` and not reusable without promotion.
- **Catch-up to live handover invariant (ADRs 0014/0008).** `CatchupSubscriptionModel` reconciles events written during the bulk replay via a delta query using `SortBy.natural(DESCENDING)` + `limit` (insertion order), NOT the time-based `catchupPhaseSortBy`. Selecting by time is loss-prone under clock skew (a backdated during-replay event sorts before the boundary and is missed by both the delta and the live resume). **Do NOT "tidy" the delta sort back to `catchupPhaseSortBy`.** The global checkpoint is captured AFTER the bulk replay (fresh token, avoids oplog ageing). #208 closed the count-to-read window by re-reading the recent tail until the matching count stops growing; `runCatchupForStream` dedups cached ids so overlapping re-reads stay at-least-once, and closes its source stream. Residuals needing a global monotonic position: net-count arithmetic loses events if events are deleted mid-replay, and `count(Filter.All)` on Mongo uses `estimatedDocumentCount`, which can undercount after an unclean shutdown. InMemory `SortBy.natural` means GLOBAL insertion order.
- **Subscription resume-marker field (do not regress #272).** `MongoCommons` writes the marker under `checkpoint` (`GENERIC_CHECKPOINT`) and keeps `subscriptionPosition` (`LEGACY_GENERIC_CHECKPOINT`) as a read-only fallback for pre-rename documents (read tries `checkpoint` first, else legacy; `replaceOne` migrates on next save). Removing the legacy read-fallback or changing either key loses not-yet-migrated consumers' resume points.
- **DCB storage.** DCB shares the CloudEvent storage boundary; metadata is CloudEvent extensions so normal subscriptions still see DCB-written events. Position reservation uses a separate collection, but event documents go into the normal event collection with stream metadata. DCB appends are transactional and rely on `MongoTemplate` session synchronization `ALWAYS`. Reads capture a high-watermark and bound matches to `dcbposition > afterSequencePosition && <= highWatermark`, returning that watermark. Append-condition concurrency updates conservative checkpoint keys (`all`, `tag:<tag>`, type-only) to detect racing appends.
- **Two different "is this a DCB event" fields, never conflate them.** `dcbTags` (capital T) is a Mongo-only derived index array, written only by `DcbDocumentMapper` on the DCB `append(...)` path, always present (empty array for zero tags), and sparse-indexed (ADR 0049) so `$exists` on it is cheap. `dcbtags` (lowercase) is the actual CloudEvent extension, present on any event a caller tagged via `DcbCloudEvents.withTags(...)` regardless of write API, and is what `DcbCloudEvents.isDcbEvent` and the in-memory matcher check. The fix for their potential divergence (#282) was NOT to switch the Mongo check to the extension (that would defeat the sparse index) but to make them provably equivalent by rejecting `dcbtags`-carrying events on the stream `write(...)` path in all four stores. New Mongo-side DCB discrimination must use the indexed `dcbTags` array; anything working with a live `CloudEvent` must use the `dcbtags` extension via `isDcbEvent`.
- **A sparse index only accelerates `$exists: true`, never `$exists: false`** (it has no entries for documents missing the field). So the DCB-side guard (#280) gets full index support while the reverse (#282) does not. Accepted as a known low-risk limitation, since the one real caller (`StreamCatchupSubscriptionModel`) always has a position-range predicate to ride on. **Do not "fix" this with a second index;** the correct fix if it ever becomes a hot path is a written marker field on stream-only events, rejected as premature (ADR 0050 has the analysis).
- **DCB partition stream-version collision retryability is MongoDB-version-sensitive (#297).** On a DCB+STREAM store, two concurrent DCB appends to disjoint boundaries can collide on the same stream version when they hash to the same partition. On 4.2.x this surfaced as a transient `WriteConflict` (auto-retried); on newer servers it can be a non-transient `E11000`, which #297 detects via the `streamid_1_streamversion_1` index name and rethrows as retryable rather than as a misleading `DuplicateCloudEventException`. Now validated against MongoDB 8.0 (#302).
- **In-memory `deleteAll()` must reset DCB sequence state**, else an emptied store reports stale DCB high-watermarks.
- **Do not gate the DCB application-service bean with `@ConditionalOnBean(TagGenerator.class)`.** That condition evaluates while bean definitions are still processing and can miss a user's `TagGenerator` in a real Boot context even though slice tests pass. It is a normal generically-typed `@Bean` resolving `TagGenerator` via `ObjectProvider.getIfAvailable()` at instantiation, returning `null` when none exists.

### Spring wiring

- **The starters mark the async `SubscriptionModel`/`Subscriptions` beans `@Primary`** because the synchronous model is also a `Subscribable`, so a bare `Subscribable`/`SubscriptionModel` injection resolves to the async one. Inject the concrete `SynchronousSubscriptionModel` to disambiguate.
- **The native `MongoEventStore` routes `read`/`query`/`count`/`exists`/`readInPositionOrder` through the thread-bound `ClientSessionHolder` when set**, so a synchronous handler sees the uncommitted write consistently. `count(Filter.all())` is the one asymmetry: it uses the fast `estimatedDocumentCount()` when no session is bound (the normal path, and the `CatchupSubscriptionModel` net-count path, both unchanged) but falls back to an exact `countDocuments(session, {})` inside an ambient session, because `estimatedDocumentCount` has no `ClientSession` overload. The slower exact count therefore only fires for a synchronous handler that itself calls `count(Filter.all())` inside the write transaction.

- **Docker/Testcontainers is the biggest verification risk.** Fixed `27017:27017` bindings clash with local Mongo or concurrent runs, and async subscription tests are timing-sensitive. Locally the suite needs `DOCKER_HOST=unix:///Users/johan/.colima/default/docker.sock` plus `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` (Testcontainers cannot auto-discover Colima). **Running many replica-set suites in one session exhausts Colima and mass-flakes container startup, so rerun failed classes in isolation before believing a failure is real.** Known env flake: `SubscriptionProjectionsWithSpringAndMongoDBApplicationTest` intermittently fails context load with `NullPointerException: BsonTimestamp ... is null`; retry.

- **A local `-am test` that dies on a container flake in an early module never reaches later modules.** When a shard fails in CI but passed locally, check whether the local run actually reached that module.
- **code-review-graph is structurally weak for architecture boundaries here** (file-based communities, no cross-community edges, test-dominated flows). Use it for inventory and impact, but verify module boundaries from Maven and source.

### Recurring correctness lessons

- **A top-level-declaration sweep misses nested public types and Kotlin free functions.** Sweep both (nested = indented type decls; Kotlin = top-level `fun`). A type-level audit that matched only non-indented declarations missed 4 renamed public nested types reachable via `switch` pattern-matching over sealed types.
- **A single failed `git show <tag>:<guessed-path>` proves a *path* does not exist, not that a *type* never existed.** Verify a type's non-existence with content search (`git grep`), never a guessed path. **The changelog cannot be trusted to list every breaking rename;** the real gaps were found by diffing every top-level type declaration between the `0.20.5` tag and HEAD (526 types audited).
- **Domain event classes fed through `ReflectionCloudEventTypeMapper.simple()` must be top-level, not nested in a sealed interface**, because `Class.forName(pkg + "." + simpleName)` cannot resolve the `Outer$Inner` binary name.
- **A recipe test's stub annotation must use the real enum constants**, not invented ones, or the rewritten before/after snippet references a constant that will not compile against the real target version.
- **Point subagents at the session worktree path.** A brief naming an absolute repo path makes edit-only subagents write to THAT checkout, not the session worktree; three subagents once edited the main checkout and their work had to be patched across.

## Build And Verification

Use `rtk <command>` wherever `rtk` supports it; raw shell only when unsupported. Managed dependency versions live in the root `pom.xml` `<properties>` and imported BOMs (Spring Boot, Reactor, MongoDB driver, Jackson 3, CloudEvents, JobRunr); do not duplicate them here.

CI: `.github/workflows/maven.yml` builds once per JDK (`install -DskipTests`, Temurin 21 and 25) and then runs the tests as 10 shards per JDK, with Testcontainers reuse via `$HOME/.testcontainers.properties`. Shard count is pinned at 10 because the account's GitHub plan allows 20 concurrent jobs; rebalance by moving paths between shards, never by adding one. Each shard reports its per-subtree timings to the run summary and as `shard-timing` log lines, and warns when it exceeds `SHARD_BUDGET_SECONDS`, so a shard that grew says so instead of quietly stretching the run; read them with `gh run view <run-id> --log | grep shard-timing`. Costs are not additive: with Testcontainers reuse the first subtree to boot MongoDB on a runner pays for the container and its neighbours ride along, so a subtree's time changes when it moves shard. Each shard pre-pulls every image the tests need and caps `pull.timeout` at 60s, so an unreachable Docker Hub fails in under a minute saying so rather than costing ~292s per test class and tripping the 20 minute job timeout (#432). Those images come from a private mirror at `ghcr.io/<owner>/occurrent-ci`, retagged to their Docker Hub names so the tests find them locally, with a `mirror-images` job filling any gap (#436). Both jobs take the list from `.github/scripts/required-test-images.sh`, which derives it instead of hardcoding tags: Mongo from `integration-tests.mongo.version`, Redis from the literal in `SpringRedisCheckpointStorageTest`, ryuk from a bytecode constant in the Testcontainers jar. Every part of that is best effort, so whatever it cannot derive, or the mirror lacks, falls back to Docker Hub with a warning rather than breaking. Do not reach for Testcontainers' `hub.image.name.prefix`: it rewrites every Docker Hub image with no per-image opt-out and no fallback, so a mirror lagging a version bump would turn into a red run. The IDE fallback for the Mongo version comes from `occurrent-test-support.properties`, filtered from the same pom property, so it cannot drift.

Local patterns:

- Full package: `rtk mvn -B package --file pom.xml`
- Focused module: `rtk mvn -pl <module-path> -am test` (or `package`, or `test-compile` for Kotlin/generics changes)
- Focused test class: `rtk mvn -pl <module-path> -am -Dtest=<TestClass> test`
- DCB touched-module set: `rtk mvn -q -pl eventstore/api/dcb,eventstore/inmemory,eventstore/mongodb/spring/blocking,application/service/blocking,subscription/mongodb/spring/blocking -am test`
- **Authoritative gate: read the log for `BUILD SUCCESS`/`BUILD FAILURE`, never trust a wrapper exit code.** Confirm the JDK is 21 (`mvn -version`).

Release: `mvn_local_snapshot.sh` runs a release-profile local install with `-Drevision=...`. `mvn_release.sh` requires Java 21, uses `mvn deploy -Prelease` with GPG signing, source/javadoc jars, Sonatype Central publishing, and tags `occurrent-<version>`.

Four load-bearing decisions from the design pass:

1. **A SQL live subscription reads change data capture, not a position poll (#397, #405).** Because positions are reserved outside the write transaction, position order is not commit order, so a `position > checkpoint` tail read can skip an event whose transaction has not committed and then advance past it forever. MongoDB is immune only because its live checkpoint is a change-stream resume token, not a position. A WAL LSN is the direct analogue, so `LsnCheckpoint` goes where `MongoResumeTokenCheckpoint` goes and `globalCheckpoint()` returns the current LSN. The maintainer chose CDC over the simpler lock-until-commit option for consistency with the Mongo architecture and to avoid serializing appends. **Coupled knob:** position strategy `sequence` (default, what CDC wants) vs `commitOrdered` (serializes appends, the only thing that makes #408's polling sound), and wiring polling over `sequence` MUST fail at startup. **Pushback the ADR has to carry:** a stalled replication slot retains WAL until the primary's disk fills (worse than Mongo's benign error 286), logical decoding needs `wal_level=logical` plus privileges that some managed instances and all transaction-pooling poolers deny, there is one slot per store and never per subscription, and CDC does not make positions dense. **ADR 0062's "a feed-derived position watermark is unworkable" line is a MongoDB consequence, not a general law, and the new ADR must say so.**
2. **The broker consume side is a bridge into `Pushable`, not a new `SubscriptionModel` (#412, #415, #417).** The push machinery already ships transport-neutral, and a broker-backed model cannot honestly implement `startAt`/replay. Seams: `EventDestination` (per transport, headers in the record from day one), `DestinationResolver` (derives routing from `CloudEventTypeMapper` so publisher and consumer agree by reading one mapping, and answers the reverse `destinationsFor(SubscriptionFilter)`), and `CloudEventSink`/`DomainEventSink` as the ONE seam a user swaps for their existing publisher wrapper (routing lives behind the sink because their wrapper already decides both). Deliberately not called a "decorator". Both directions work at the CloudEvent AND domain-event level, with domain types in the same artifact as their transport, in a separate package. **Two invariants:** the Occurrent extensions travel as message headers at both levels (otherwise `EventMetadata` breaks and #389 gets worse), and filter-derived bindings only narrow what arrives while `SubscriptionFilterMatcher` still decides.
3. **A SQL Spring Boot starter needed #409 first, and #409 is DONE** (ADR 0072). See the annotation-module section above for what a store starter now owes. The remaining gap for #410 is `OccurrentProperties`, which is store-neutral in code but not in configuration surface.
4. **DDL ownership is an explicit decision, not a port of Mongo's behavior (#398).** Mongo creates missing indexes per enabled capability at startup, which does not transfer to a production relational database, so this needs shipped DDL, opt-in auto-create for dev/test, and a documented Flyway/Liquibase path.

Docs (#420, #421) follow the release-gated held-branch convention, and **#420 must carry the CDC operational prerequisites** (`wal_level`, privileges, managed-instance parameters, slot-lag monitoring), because getting those wrong takes a database down.

### Consciously not done (would be net-negative, do not re-raise)

- A shared `SnapshotDocuments` Mongo helper: no clean shared module for ~15 lines, so adding a dependency is overengineering.
- Collapsing the start-position converters via `Enum.valueOf(name)`: trades a compile-time-exhaustive switch for runtime name-coupling.
- **"Agnostic `Subscriptions` delivering DCB events makes `EventMetadata.streamId` crash" is FALSE.** DCB events are stored via the shared stream mapper with a generated partition stream id, so `EventMetadata.streamId` returns that partition id.
- **Documented gaps consciously accepted for this release:** no reactive competing-consumer model (ADR 0044), and reactive `@StreamSubscription` cannot honor a specific historical start time (ADR 0045). - **Cross-store sort caveat:** a natural sort step combined with other sort steps is a valid insertion-order tiebreaker in-memory but is rejected by the MongoDB stores (documented on `SortBy.natural`), because MongoDB cannot express a natural sort inside a compound sort.
